# pokecrystal16 Pokémon pic format

Everything here was read from this repo (`gfx/pokemon/`, `Makefile`, `tools/*.c`,
`data/pokemon/palettes.asm`, `data/pokemon/base_stats/*.asm`). The converter
(`convert.py`) is built to match it.

Entries inspected: **pichu** (40x40, 5 frames), **bulbasaur** (40x40, 6 frames),
**cyndaquil** (40x40, 5 frames), **pikachu** (40x40, 6 frames), **kakuna**
(40x40, 2 frames, the simplest animation in the repo), **onix** (56x56, 9 frames),
plus a survey of all 277 `front.png` and 276 `back.png` files for sizes, modes
and placement. Bayleef, chansey and charmeleon were checked as 48x48 examples.

## Folder contents (what is actually checked in)

```
gfx/pokemon/<name>/
    front.png       source, hand-made
    back.png        source, hand-made
    shiny.pal       source, hand-made
    anim.asm        source, hand-made
    anim_idle.asm   source, hand-made
```

There is **no `normal.pal` per Pokémon.** The normal palette is read out of
`front.png` + `back.png` at build time (see "Palettes" below). The only
`normal.pal` in the tree is `gfx/pokemon/unown/normal.pal`, which is a special
case for the shared Unown palette.

`frames.asm`, `bitmask.asm`, `front.dimensions`, `front.animated.tilemap`,
`*.2bpp`, `*.lz` and `*.gbcpal` are **generated by `make`**. The frames and
bitmasks are gitignored (`.gitignore`: `gfx/pokemon/*/frames.asm`, …) and
`make clean` deletes them. You never write them by hand.

## front.png

- Indexed PNG (`P` mode), 8-bit depth, exactly **4 palette entries** in a `PLTE`
  chunk plus a `tRNS` chunk of four `0xFF` bytes (all opaque). 251 of 277 have
  the tRNS chunk and 26 don't; it makes no difference to rgbgfx.
- Palette order as stored: **index 0 white, 1 light color, 2 dark color,
  3 black**, e.g. pichu `(255,255,255) (239,214,41) (214,49,0) (0,0,0)`.
- Background is index 0 (white). White inside the body (eyes, highlights) is
  the same index 0. There is no transparency.
- **Width** must be 40, 48 or 56 (`tools/png_dimensions.c` errors on anything
  else). Distribution in vanilla: 103 at 40, 84 at 48, 90 at 56.
- **Animation frames are stacked vertically**: the image is `W` wide and
  `W * N` tall, each frame a `W x W` square. Frame 0 (top) is the base pic.
  Frames 1..N-1 are the alternate poses. In vanilla N ranges from 2 (kakuna,
  gligar) to 14 (celebi).
- `tools/pokemon_animation_graphics.c` cuts the stack into `W/8 x W/8`-tile
  frames, keeps frame 0 whole, and dedupes tiles in later frames against it.
  `tools/pokemon_animation.c` then emits, per extra frame, the changed tiles
  (`frames.asm`) and a bitmask of which tiles changed (`bitmask.asm`).
  `num_frames = total_frames - 1`, so a single-frame front.png produces an empty
  `frames.asm`/`bitmask.asm` (zero extra frames). The converter defaults to
  that; `--frames 2` duplicates the pose to copy kakuna's 2-frame layout exactly
  if you'd rather not rely on the zero-frame case.
- Placement (survey of frame 0): the sprite is **horizontally centered**
  (median offset 0) and sits on the bottom edge. Bottom gap is 0 px for 135
  sprites, 1 px for 87, 2 px for 31, rarely more.
- `data/pokemon/base_stats/<name>.asm` does
  `INCBIN "gfx/pokemon/<name>/front.dimensions"`, which is one byte
  `(w/8 << 4) | (w/8)` produced from the PNG width. Changing the size class
  needs no asm edit.

## back.png

- Indexed PNG, 4 colors, same palette order and same palette *values* as the
  front (both come from one `normal.gbcpal`).
- Always **48x48**, a single frame (all 276 are 48x48).
- Built with `rgbgfx --columns` (column-major tiles); that's a build flag, not
  something the PNG needs.
- Placement: bottom-aligned (bottom gap 0 px for 254 of 276); many are cropped
  by the bottom edge on purpose. Top gap varies.

## Palettes

The colors are 15-bit GBC colors (5 bits per channel, 0–31).

### Normal palette (generated)

```
gfx/pokemon/%/normal.gbcpal: gfx/pokemon/%/front.gbcpal gfx/pokemon/%/back.gbcpal
	tools/gbcpal $(tools/gbcpal) $@ $^
%.gbcpal: %.png
	$(RGBGFX) -p $@ $<
```

1. `rgbgfx -p` dumps each PNG's palette as little-endian 15-bit words
   (`0bbbbbgggggrrrrr`).
2. `tools/gbcpal.c` concatenates front + back colors, **sorts by luminance**
   (`0.299r + 0.587g + 0.114b`, lightest first), drops exact black, exact white
   and adjacent duplicates, and keeps the first two as the middle colors:
   `[WHITE, lighter, darker, BLACK]`. Some mons in the Makefile use `--reverse`
   (spearow, jynx, porygon…), which swaps the ordering.
3. `data/pokemon/palettes.asm` includes only the middle two colors:
   `INCBIN "gfx/pokemon/<name>/normal.gbcpal", middle_colors`.

What this means for the converter:

- front.png and back.png must use **the same two middle colors**. If back.png
  had a third distinct color, `gbcpal` could keep it and drop one of the
  front's.
- Middle colors must never be exactly (0,0,0) or (31,31,31). `gbcpal` would
  filter them out.
- Index 1 has to be the lighter color, so the luminance sort keeps the pixel
  indices in line with the palette.

### 8-bit PNG value ↔ 5-bit GBC value

The PNG palettes hold 5-bit values expanded as `v8 = (c << 3) | (c >> 2)`:
pichu `239,214,41` = `29,26,5`; `214,49,0` = `26,6,0`. The converter snaps every
color to 5 bits and expands it the same way, so the round trip is exact.

### shiny.pal (hand-written)

Plain text: a blank line, two `RGB r, g, b` lines (tab-indented, two-digit
zero-padded 5-bit values), then a trailing blank line. Light color first, dark
second:

```

	RGB 31, 17, 00
	RGB 20, 02, 11

```

(bytes: `0a 09 "RGB 31, 17, 00" 0a 09 "RGB 20, 02, 11" 0a 0a`)

Included directly: `INCLUDE "gfx/pokemon/<name>/shiny.pal"`. 252 mons have
one. 25 folders don't (unown_* letters, egg, etc.).

## anim.asm / anim_idle.asm

Animation scripts using the macros `frame <index>, <duration>`,
`setrepeat <n>`, `dorepeat <label>`, `endanim`. `frame 0` is the base pic.
`frame k` is the k-th extra frame in the stack. One tab of indent, two-digit
durations. Simplest vanilla example (kakuna, 2 frames):

anim.asm
```
	frame 0, 12
	frame 1, 24
	endanim
```
anim_idle.asm
```
	setrepeat 2
	frame 0, 07
	frame 1, 07
	dorepeat 1
	endanim
```

For a single static frame the converter writes the same shape with only
`frame 0` (`frame 0, 12` / `frame 0, 24` / `endanim`, and the idle loop on
`frame 0`), so no frame index past the end is ever referenced.

## Wiring a new mon into the build (NOT done by the tool)

For reference only. The converter does not touch any of these:
`gfx/pics.asm` (`<Name>Frontpic`/`Backpic` INCBINs), `gfx/pokemon/anims.asm`,
`idles.asm`, `bitmasks.asm`, `johto_frames.asm`/`kanto_frames.asm`, the
`*_pointers.asm` tables, `data/pokemon/palettes.asm`,
`data/pokemon/base_stats/<name>.asm` (front.dimensions INCBIN), and the
Makefile's `--reverse` list if needed.
